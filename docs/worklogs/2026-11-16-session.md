## 지속 개발과 장비 관리 1차

교수님의 지속 개발 요청에 따라 계획서와 코드를 검토하고 장비 관리(F08), 학생 신청 상세, 시설 운영 관리(F21), 개인 홈·모바일, 대체 관계 편집(F17)의 보완 순서를 제안했다. 사용자의 개선 시작 요청에 따라 F08을 먼저 구현했다.

- 관리자 `/admin/equipment` 화면과 API에서 분류·모델·사양 등록, 개별 장비 등록·수정, 구성품 편집, 대여 허용·사용 중지를 제공한다.
- 학생 목록과 검색 필터에 새 장비·분류를 반영한다. 등록된 관리번호는 이력 식별자로 유지한다.
- 행 잠금·기대 버전 검사로 동시 수정을 처리한다. 운영 변경에는 사유와 실제 영향 확인을 요구한다.
- 진행 중 신청이 있으면 모델·기본 구성품 변경을 제한한다. 과거 출고·반납은 보존된 구성품 기준을 사용한다.
- 반납 검수에서 손상·누락을 발견해도 관리자의 사용 중지 설정을 유지한다. 미해결 반납과 출고 관련 미완료 점검의 정상 복귀 우회를 차단한다.
- 공유 모델의 사양 변경은 새 모델 등록 후 해당 장비에 선택하는 방식으로 구현했다. 공유 분류·모델 정의 편집은 남은 범위다.
- 작업 중 별도로 반영된 Java 25 설정을 유지하고 준비된 Java 25.0.4.1 환경에서 검증했다. 시스템 Java 8은 단독 DB 검사 도구에서 계속 사용한다.

이전 F08 작업에서 단위 테스트 18개, 실제 Oracle API 11개, Chrome 화면 13개와 기존 추천·가용성 검사 15개, JAR 패키징을 통과했다. 실제 서버 검증은 합성 데이터로 수행했으며 생성한 계정·장비·분류·모델·신청 등 45행을 고유 식별자로 한정하여 정리했다. 초기 핵심 업무 API 20개와 화면 20개는 앞선 Java 21 검증 결과다. 이번 Git 공유 단계에서는 기존 결과·파일 무결성과 공개 변경 내용을 확인했다.

## 포스터 참고와 화면 이미지 추출

다른 팀이 제공한 초안 세 개를 읽고 시스템 소개·기획 단계 문제 가설·구현 화면·개발 스택을 한 페이지에 배치하는 구성을 검토했다. CampusRent의 중심 설명은 목적·인원에 따른 규칙 기반 자원 추천과 신청부터 출고·반납까지의 관리 흐름으로 정리했다.

포스터 제작 도구로 Figma Design을 제안했다. 화면 캡처·문구·구성도 배치와 PDF 내보내기에 활용하고, 발표자료는 PowerPoint로 준비하는 흐름을 논의했다. 최종 포스터·발표자료·보고서는 앞으로 준비할 산출물이다.

사용자가 제공한 `New-Era 화면설계서_20261026.pptx`와 `New-Era 화면설계서_20261027.pdf`의 39쪽 구성과 화면 ID를 대조했다. PPT에 포함된 PNG 37개를 원본 바이트 그대로 추출해 `output/poster-screenshots`에 정리했다.

- 포스터 핵심 후보 12개와 보조 화면 25개
- 추천·검수의 분리 영역을 나란히 배치한 이미지 4개
- 핵심 화면 미리보기, 화면 ID·쪽수·해상도·SHA256 목록, 사용 안내
- `output/CampusRent_포스터_화면이미지.zip` 전달본

추출 이미지는 10월 설계서에 수록된 시연 화면이다. 다른 팀의 참고 PDF와 개인 폴더의 원본 문서는 로컬 참고자료로 사용했다. 이번 공유에는 CampusRent에서 추출한 화면 이미지·사용 안내·압축 전달본을 포함한다.

## 로컬 수정·Git 공유 원칙

**각자 VS Code의 로컬 작업 폴더에서 파일을 수정하고 로컬 Git으로 Commit·Push한다. GitHub에 직접 로그인해 브라우저에서 파일을 수정하지 않는다.** 사용자가 이번 공유 요청에서도 이 원칙을 다시 확인했다.

공개 후보와 커밋에 등록된 실제 파일 내용을 로컬 비밀값과 비교한 뒤 공유한다. 실제 설정·환경변수 파일·런타임·캐시·빌드·합성 계정 정보는 Git 제외 상태로 관리한다. 포스터 전달 ZIP 한 개는 해당 경로에 한정해 공유한다.
