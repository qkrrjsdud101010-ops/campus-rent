# 2026-11-18 CampusRent 대화·작업 기록

## Git 공유 요청

사용자가 누적 개발 변경과 대화·검증 기록의 커밋·푸시를 요청했다. 로컬 Git으로 origin/main에 공유하며 GitHub 브라우저 수정은 사용하지 않는다. 시설 운영·대체 관계·신청 상세·개인 홈·추천 및 선택형 문장 분석의 구현·테스트·문서를 포함한다. 실제 OpenAI 호출의 HTTP 429와 남은 검증은 성공 기록과 구분한다. 공개 설정 예시의 OpenAI 키 항목은 환경변수 참조로 정리했다. 실제 로컬 설정·API 키·DB 비밀번호·로컬 검증 산출물은 제외한다.

## 후속 확인: 키 등록 및 실제 OpenAI 1회 호출

사용자의 입력 완료 안내 후 로컬 키 등록을 값 노출 없이 확인하고 확인된 8081 서버만 재시작했다. 설정·기존 키·DB 설정·모델(gpt-5.4-mini)은 유지했다. 실제 기능 조회는 provider=openai/available=true/externalProcessing=true였다. CSRF 세션을 유지한 지정 문장 POST 1회는 OpenAI HTTP 429를 받아 source=rules/reason=rate-limited/analysis=null로 대체됐다. 새 서버의 첫 유효 분석 요청이므로 로컬 분당 제한이 아닌 외부 제공자의 제한으로 판별한다. 구체적인 error.code는 보관되지 않아 잔액·사용량·속도 제한 중 원인은 확정하지 않았다. 반복 호출은 하지 않았다.

이번 HTTP 검사 7개와 Oracle 카탈로그 조회, 키 등록 후 Git·공개 변경 파일·기존 JAR의 비밀 제외를 확인했다. 애플리케이션 코드 변경·새 빌드·테스트 재실행·브라우저 추가 조작·예약 제출·DB 생성/초기화/삭제·커밋/푸시는 하지 않았다. 앞선 Java 97개·JS 28개 통과와 구분한다. 실제 AI 결과·확인 적용·품질·지연과 결제·모델 권한은 미검증이며 계정 한도 확인 후 이어서 검증한다. 8081 서버는 실행 중이다.

## 후속 재점검: 8081 OpenAI 연결 준비와 실제 실행

사용자의 상세 점검 요청에 따라 기존 구현·설정·테스트·실행 스크립트·비밀 제외 규칙을 확인했다. 이번 변경은 실제 Git 제외 로컬 파일의 분석 설정 활성화와 문서 기록 갱신이다. DB 설정·기존 키는 보존하며 애플리케이션 소스·모델·ERD·DB 데이터는 변경하지 않았다.

OpenAI 키는 로컬 설정과 프로세스·사용자·시스템 환경변수 모두 미등록이었다. 실제 로컬은 enabled=true/provider=openai/환경변수 키 참조/gpt-5.4-mini/8000ms/분당20회로 준비했다. run-server.cmd로 8081 서버를 실행하고 CSRF 세션을 유지해 지정 문장을 유효 POST 1회로 확인했다. 응답은 source=rules/reason=unconfigured/analysis=null이며 실제 외부 호출은 0회다. 서버 HTML·Oracle 카탈로그와 오류 입력까지 로컬 HTTP 8개 검사가 통과했다. Java 97개·JS 28개를 재실행했고 기존 JAR·Git의 비밀 제외를 재확인했다. 애플리케이션 코드 수정이 없어 이번 새 JAR 빌드는 실행하지 않았다.

브라우저에서 8081 목적별 페이지 준비 상태까지만 관찰했다. 창 최소화 후 자동 제어가 복구되지 않아 분석 확인 적용·추천 결과의 실브라우저 점검은 미완료다. 실제 GPT 응답·품질·지연·결제·모델 권한도 키 입력 전 미검증이다. 예약 제출·운영 DB 생성·초기화·삭제·커밋·푸시는 수행하지 않았다. 키는 실제 application-local.properties에만 입력하며 .example·채팅에는 입력하지 않도록 안내했다. 세부 결과는 [문장 분석 안내](../SENTENCE_ANALYSIS.md)를 따른다.

## 후속 변경: GPT(OpenAI) 연결 선택

- 사용자가 Gemini 대신 GPT 연결을 요청하여 기본 제공자를 `openai`, 모델을 `gpt-5.4-mini`로 설정했다. OpenAI Responses API의 strict JSON Schema를 사용하고 `store=false`, 출력 토큰 768개 제한을 명시한다.
- 공통 프롬프트·제한된 HTTP 전송을 분리하고 완료·정형 응답만 적용한다. 거절·불완전·도구 호출·추가 필드·중복 JSON·오류 응답은 기본 규칙으로 대체한다. 자동 재시도와 다른 제공자에 대한 자동 전환은 없다.
- OpenAI 키는 Git 제외 로컬 설정의 `campus.analysis.openai.api-key` 또는 `OPENAI_API_KEY`로만 관리한다. 기존 Gemini 키와 분리했다. 키 입력 전에는 `campus.analysis.enabled=false`로 유지한다.
- 전체 Java 97개와 JAR 패키징, 분석 화면 로직 대역 8개, 서버 요청 옵션 대역 4개를 통과했다. 로컬 서버 재시작 후 HTTP 9개 검사 및 기본 제공자 OpenAI·중지 상태를 확인했다. 비밀 설정의 Git 제외·JAR 미포함 검사를 통과했다.
- 실제 OpenAI 모델 호출·품질·지연은 키 입력 후 검증한다. 분석 확인 화면의 실브라우저 동작은 미검증이다. DB 스키마 변경·실데이터 수정·Git 커밋 및 푸시는 진행하지 않았다.

## 후속 추가: 선택형 AI 문장 분석

사용자가 문장 분석 구조의 개발을 승인했고, 외부 API 키를 발급해 연결하는 방식을 선택했다. Gemini 어댑터와 교체 가능한 제공자 경계, 공개 분석 API(CSRF 유지), 분석 결과 비교·필드별 확인 적용 화면을 구현했다. AI는 활동·인원·준비 항목만 제안하고 실제 시설 허용 목적·날짜·자원 ID·예약을 지정하지 않는다. 수동 설정·기존 선택을 보존하고 오래된 응답을 폐기한다.

기본은 외부 분석 중지 상태이며 키는 Git 제외 로컬 파일·환경변수에서 관리한다. 실제 키는 아직 입력되지 않았고 발급 방법을 안내했다. 기존 ERD·DB 데이터는 변경하지 않았다. Java 전체 90개(기존 79+신규 11)·분석 화면 로직 대역 8개·서버 API 옵션 대역 4개·기존 추천 엔진 16개와 JAR 패키징을 통과했다. 실제 로컬 HTTP의 기능 조회·CSRF·기본 규칙 대체·입력 거부·정적 파일도 확인했다. 실제 Gemini 모델 호출·품질·지연과 이번 분석 화면의 실브라우저 검증은 남아 있다. 연결 절차는 [문장 분석 안내](../SENTENCE_ANALYSIS.md)를 따른다. 커밋·푸시는 실행하지 않았다.

사용자는 **신청 상세 → 시설 운영 관리 → 대체 장비 관리 → 개인 홈·모바일** 순서의 개발을 승인했다. 기존 기능 ID와 ERD 명칭·26개 테이블·17개 시퀀스를 유지하며 기존 초기 자원이나 신청 이력을 삭제하지 않는 범위로 진행한다.

신청 상세·시설 운영 관리(F21)·대체 장비 관계 관리(F17 관리 부분)·개인 홈(UX02)·모바일 선택 목록(UX05)을 구현했다. Java 단위 테스트 73개·실제 Oracle API 42개·JavaScript 순수 검사 47개·JAR 패키징을 통과했다. 실제 브라우저 검증은 자동화 연결 오류로 수행하지 못했다. 이전 검증 수치를 이번 새 기능의 통과 결과로 합산하지 않는다.

## 1. 신청 상세와 학생 응답

학생의 `/records`·`/history`에서 기존 자원 상세와 신청 항목의 진행 상세를 구분했다. `?item={requestItemId}` 연결을 통해 해당 항목을 열고 현재 진행·종료 분류와 접근 권한을 따른다.

- 현재 상태·예정 일정·다음 행동과 승인 대기 미확보 안내를 표시한다.
- 실제 처리 이력과 출고·시설 이용 시각을 사용하며 예정 시간 경과로 완료를 추정하지 않는다.
- 출고 당시 구성품 기준, 반환 회차·이번 반환량·누적량·남은 수량과 보류 사유를 표시한다.
- 학생 응답에서 관리자 내부 검수 메모·식별정보를 제외한다. 학생에게 공개하는 거절·보류 사유는 별도로 유지한다.
- 기존 취소·반납 신청·관리자 검수와 역할·소유권·버전 정책을 유지한다.

상세 조회는 기존 `GET /api/requests`의 권한별 기록을 사용한다. 별도 `/api/me/request-items/{id}` API를 구현한 것으로 표기하지 않는다.

## 2. F21 시설 운영 관리

관리자 화면 `/admin/facilities`와 `/api/admin/facilities`를 추가했다. 시설 기본 정보, ISO 요일 1~7의 같은 날 운영 시간, 허용 목적, 점검·운영 중지 구간을 편집한다. 시설 관리번호는 등록 후 유지하며 미설정 시간·목적을 종일 이용 가능으로 추정하지 않는다.

| 경로 | 동작 |
| --- | --- |
| `GET /api/admin/facilities` | 시설·목적·시간·제한 구간 조회 |
| `POST /api/admin/facilities` | 신규 시설 등록 |
| `PUT /api/admin/facilities/{id}` | 시설 정보·요일 시간·목적 수정 |
| `POST /api/admin/facilities/{id}/blocks` | 제한 구간 추가 |
| `PUT /api/admin/facilities/{id}/blocks/{blockId}` | 제한 구간 수정 |
| `POST /api/admin/facilities/{id}/blocks/{blockId}/remove` | 제한 구간 삭제 |

시설 행의 `ROW_VERSION`을 정보·구간 변경이 공유한다. 신청 제출·승인과 동일한 부모 시설 행을 먼저 잠그고 기대 버전·예약 영향을 검사한 뒤 원자 저장한다. 미래 승인 예약과 실제 종료 처리되지 않은 이용을 보호한다. 수용 인원 축소·목적 제거·요일 시간 변경·이용 불허·운영 중지·제한 구간이 예약을 무효화하면 `409`로 거부하며 자동 취소하지 않는다. 승인 대기 신청은 변경 후 승인 시 최신 조건을 재검사한다.

운영 상태·이용 허용 변경과 제한 구간 변경에는 사유·실제 확인을 요구한다. 제한 구간 수정은 등록자·최초 등록 시각을 보존한다. 기존 승인·사용 이력을 수정하지 않는다. 구간의 등록·수정 사유는 기존 `REASON_TEXT`에 저장하며 별도의 시설 상태 변경·삭제 감사 이력은 추가하지 않았다.

## 3. F17 대체 장비 관계 관리

관리자 화면 `/admin/alternatives`와 API `/api/admin/equipment-alternatives`를 추가했다. 원래 장비에서 대체 장비로 향하는 방향 관계와 관계별 지정 사유·주요 차이·활성 여부를 편집한다.

`GET /api/admin/equipment-alternatives`는 장비와 활성·비활성 관계를 반환한다. `PUT /api/admin/equipment-alternatives/{sourceId}`는 다음 형태의 전체 목록을 받는다.

```json
{
  "expectedVersion": 0,
  "alternatives": [
    {"targetId": "2", "reason": "관리자가 확인한 대체 지정 사유", "difference": "주요 차이", "enabled": true}
  ]
}
```

예시는 요청 형식 설명이며 실제 저장된 자산·장비 번호를 의미하지 않는다. 관계는 `A → B`이며 반대 방향을 자동 생성하지 않는다. 자기 자신·중복·존재하지 않는 대상은 거부한다. 사유는 관계마다 필수 500자, 차이는 선택 1000자다. 현재 장비 상태와 관계 편집 가능 여부를 구분하며 실제 학생 후보는 최신 가용성 검사를 따른다.

원래 장비 행을 잠그고 `expectedVersion`을 검사한다. 빠뜨린 기존 관계는 삭제하지 않고 비활성으로 보존한다. 실제 변경에만 원래 장비 버전을 증가시키고 `CONFIGURED_BY`를 마지막 설정자로 갱신한다. `CREATED_AT`는 최초 등록 시각을 유지한다. 같은 값 저장은 버전·설정자·시각을 변경하지 않는다.

시설·대체 관계의 목록은 부모 버전을 자식 정보보다 먼저 읽는다. 동시 수정 시 이전 내용이 최신 버전으로 저장되는 문제를 방지한다. API에는 기존 관리자 권한·CSRF를 적용한다.

## 4. 개인 홈·모바일 개선

UX02는 `GET /api/me/summary`로 로그인 학생 본인의 오늘 일정·다음 할 일을 요약하고 신청 상세로 연결한다. `basisDate`·`generatedAt`·`timeZone`, `counts`의 `pickup`·`returnDue`·`facilityUse`, `todo` 최대 3건을 반환한다. 항목 기준 집계, Asia/Seoul 날짜 경계, 승인 대기 미확보, 반납 신청·보류의 구분, 조회 실패와 0건 구분을 적용했다. 할 일은 보류·반납 신청을 우선하고 현재부터 7일 미만의 예정 행동을 채운다. 알림 발송이나 별도 연체 관리 기능을 추가하는 범위가 아니다.

홈 카드에서는 `/records?view={today-pickup|today-return|today-facilities}&date={basisDate}`로 해당 날짜·상태의 본인 내역에 연결하고 할 일은 `?item={requestItemId}` 상세로 연결한다.

UX05는 모바일 하단에서 현재 선택 수와 목록 열기를 제공하고 네이티브 `dialog`에서 같은 항목별 조건을 확인·수정·제거한 뒤 신청하도록 구현했다. 필요한 로그인과 별도 최종 확인으로 연결하고 기존 선택 상태·입력을 유지한다. 실제 화면의 본문·오류·최종 버튼 가림, 키보드 초점·닫기·복귀는 브라우저 연결 복구 후 검증해야 한다.

## 7. 추가 요청: 면접·기타 자유 활동 추천

앞선 네 단계 이후 사용자는 서버에서 `면접` 검색 시 관련 추천이 없고 `기타` 활동을 자유롭게 설정하기 어렵다는 개선을 요청했다. 면접·모의면접 준비, 스터디, 세미나·행사 인식과 자유 활동 입력을 보강하고 공간·영상 촬영·음성 녹음·자료 투사의 필요 항목을 직접 고르게 한다. AI 추천 모델 대신 규칙과 사용자의 필요 선택을 사용한다.

활동 설명과 시설의 실제 허용 목적은 구분한다. `면접 준비`는 활동으로 인식하되 학교의 허용 목적을 임의 등록하지 않는다. 기존 일정·직접 수정한 인원·허용 목적·기존 선택 목록을 보존하며 신청은 등록된 시설 목적과 최신 조건을 확인한다.

서버 카탈로그에 공개용 `purposeRules`를 추가했다. 기존 목적·키워드·장비 규칙 테이블의 활성 데이터만 읽고 일치 방식·포함/제외·우선순위·장비 필요 수준을 엔진에 전달한다. 기존 목적 목록을 유지하고 개인정보·관리자 식별자를 노출하지 않는다. 새 DDL·DB 목적·추천 정책을 임의 추가하지 않았다.

추가 개선의 검증은 다음과 같다. 5절의 Java 73개·API 42개·순수 검사 47개는 앞선 네 단계의 결과로 유지한다.
