# CampusRent 서버 개발 안내

선택형 문장 분석 API와 확인 화면을 추가했다. `GET /api/recommendations/analysis-capabilities`, `POST /api/recommendations/analyze`는 비로그인 탐색을 지원하되 POST의 CSRF 검사는 유지한다. 사용자 선택에 따라 기본 제공자는 OpenAI GPT다. 키 등록 후 8081 서버를 재시작했으며 기능 조회는 `available=true`다. 실제 외부 분석 1회는 OpenAI HTTP 429로 `rules / rate-limited`에 대체되어 GPT 성공 응답은 아직 미검증이다. 429의 잔액·사용량·속도 제한 원인은 계정에서 확인해야 한다. 이전 Java 97개·JAR 패키징 통과 기록과 실제 외부 호출 결과는 [문장 분석 안내](SENTENCE_ANALYSIS.md)에서 구분한다.

2026-11-04 Spring Boot·Thymeleaf 화면과 배정된 Oracle 11g XE 스키마를 연결했고, 2026-11-18 신청 상세·시설 운영 관리·대체 장비 관계·개인 홈·모바일 선택 목록을 보강했다. Java 단위 테스트 73개와 실제 Oracle API 42개를 통과했다. 이번 실제 브라우저 검증은 자동화 연결 오류로 수행하지 못했다. 실제 접속 주소·계정·비밀번호는 Git 제외 로컬 설정에서만 관리한다. 외부 배포와 학교 포털·하이클래스 SSO는 아직 구현하지 않았다.

## 실행

2026-11-18 재점검에서는 `run-server.cmd`로 **8081** 실제 개발 서버를 실행하고 서버 모드 HTML·Oracle 카탈로그·분석 API를 확인했다. 로컬 분석은 활성화했지만 OpenAI 키가 없어 기능 조회는 `provider=openai, available=false`, 지정 문장 POST는 `source=rules, reason=unconfigured`였다. 외부 OpenAI 호출은 수행되지 않았다. Java 97개와 JS 28개 검사를 재실행해 통과했다. 기존 JAR·Git의 비밀 설정 제외도 재확인했다. 이번 코드 변경·새 JAR 빌드는 없으며 앞선 패키징 기록과 구분한다. 브라우저는 8081 페이지 준비 상태까지만 확인했고 최소화된 창의 자동 제어 복구 실패로 확인 적용·추천 화면은 미검증이다. 키 입력 후 실제 호출과 화면 검증이 남아 있다. 자세한 상태는 [문장 분석 안내](SENTENCE_ANALYSIS.md#2026-11-18-8081-개발-서버-재점검)에 기록한다.

Windows PowerShell에서 저장소 루트를 기준으로 실행한다. 이미 이 PC에는 도구 준비가 끝나 있다.

```powershell
# 새 PC에서 한 번: 공식 배포 파일과 고정 체크섬을 검증해 .work/runtime에 준비
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\setup-server-runtime.ps1

# 실제 설정은 예시를 복사해 로컬에서 작성한다. 기존 실제 파일을 덮어쓰지 않는다.
# src/main/resources/application-local.properties.example → application-local.properties

.\run-server.cmd
```

[개발 서버](http://127.0.0.1:8081)에 접속한다. `Ctrl+C`로 종료한다. 이미 서버가 실행 중이면 중복 실행하지 않는다. 다른 포트는 아래처럼 지정한다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\server.ps1 -Task run -Port 8082
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\server.ps1 -Task test
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\server.ps1 -Task package
```

전용 Java 25 LTS와 Maven 3.9.16을 사용하며 시스템 Java 8·전역 PATH는 변경하지 않는다. Spring Boot 4.1.2, JdbcTemplate, HikariCP, Spring Security를 사용한다. 서버 JDBC는 `ojdbc8:19.33.0.0`이다. 초기 핵심 Oracle 11.2.0.2.0 API 통합 검증은 JDK 21에서 수행했고, F08 API 11개와 브라우저 13개·단위 테스트 18개는 VS Code가 제공하는 JDK 25.0.4.1에서 검증했다. 이 확인이 모든 JDK·DB 조합의 공급사 인증을 의미하지는 않는다. Java 8용 단독 SQL 검사 도구의 `ojdbc6:11.2.0.4`와 구분한다.

서버는 `127.0.0.1`에만 바인딩한다. 로컬 설정은 저장소 루트의 상대 경로에서 읽으므로 루트에서 실행한다. 패키지에도 이 파일을 포함하지 않는다. 네트워크 접근이 가능한 수업 DB 환경이 필요하며, DB 장애 시 데모 데이터로 자동 전환하지 않는다. 원문 JDBC 오류·SQL·접속 설정은 응답에 노출하지 않는다.

## 계정과 초기 데이터

학생은 화면의 **회원가입**으로 생성한다. 비밀번호는 BCrypt로 해시하여 `APP_USER`에 저장하며 공개 회원가입의 역할은 항상 STUDENT다. 로그인은 HttpOnly·SameSite=Lax 세션 쿠키, 변경 요청은 CSRF 토큰을 사용한다. 브라우저 저장소에는 비밀번호나 인증 토큰을 기록하지 않는다.

초기 관리자 로그인 정보는 이 PC의 Git 제외 `src/main/resources/application-local.properties` 안의 `campus.bootstrap.admin.email`과 `campus.bootstrap.admin.password`에서 확인한다. **DB 접속 계정과 별개인 애플리케이션 계정**이다. 공개 시연 계정은 실제 서버 로그인에 사용할 수 없다.

새 스키마에서 관리자를 준비하려면 로컬의 두 관리자 값을 입력하고 `campus.bootstrap.enabled=true`로 한 번 실행한 뒤 false로 되돌린다. 기존 학생을 관리자로 승격하거나 기존 관리자 비밀번호를 덮어쓰지 않는다. `campus.seed-demo-catalog=true`는 가상 장비 7개·시설 5개와 관련 사양·구성품·운영 시간·대체 관계를 초기 입력한다. 이 PC의 배정 스키마에는 최초 준비를 완료했으며 두 플래그는 false다. 초기 데이터는 실물 재고·학교 운영 정책이 아니다. 앱 시작 시 DDL이나 설치 SQL을 실행하지 않으며, 기존 자원을 삭제하지 않는다.

## 저장·처리 방식

| 기능 | 서버 동작 |
| --- | --- |
| 자원·가능 시간 조회 | Oracle 자원·운영 시간·승인 기간·제한 조회, 공개 응답에 신청자 정보 제외 |
| 선택 목록 | 탭의 sessionStorage에 임시 보관, 로그인만으로 제출하지 않음 |
| 신청·내역 | 인증 학생의 신청 저장, 본인 신청만 조회·취소·반납 신청 |
| 승인 | 자원 행 잠금 → 최신 중복 기간 검사 → 상태·처리 이력 원자 저장 |
| 출고 | 승인 장비의 구성품 검수 및 불변 출고 기준 저장 |
| 반납 | 회차별 이번 반환량 저장, 원래 출고 기준 대비 누적량·누락 계산 |
| 점검 | 보류·손상 시 점검 유지, 반환 완료 후 별도 확인으로 정상 복구 |
| 시설 이용 | 관리자가 실제 시작·종료 시각 저장, 조기 종료해도 원래 승인 기간 유지 |
| 신청 상세 | 본인 항목의 실제 처리·검수·이용 이력 표시, 학생 응답에서 관리자 내부 메모 제외 |
| 시설 운영 관리 | 시설 부모 행 잠금·버전 검사 후 운영 조건·제한 구간 변경, 승인 예약·진행 중 이용과 충돌 시 거부 |
| 대체 관계 관리 | 원래 장비 행 잠금·버전 검사, 방향 관계·사유·차이·활성 여부 저장, 누락 관계는 비활성 보존 |
| 개인 홈 요약 | 학생 본인 항목을 한국 시각으로 집계, 오늘 건수 3종·다음 할 일 최대 3건 반환 |
| 충돌 | 항목 버전·장비 버전과 역할·소유권 검사, 오래된 처리 거부 |

승인 대기는 자원을 확보하지 않는다. 승인·출고·반납·점검·시설 이용 처리는 같은 서비스 트랜잭션으로 저장한다. `/api/admin/**`는 관리자만 호출할 수 있다. 주요 API는 `/api/auth/*`, `/api/catalog`, `/api/requests`, `/api/admin/requests/{number}/items/{id}/actions`다.

`preview.cmd`의 8080 정적 화면은 기존 독립 시연으로 남아 있다. 서버 렌더링 시 `data-backend=server`가 적용되고 API 어댑터를 사용한다. 정적 시연과 실제 Oracle 개발 데이터를 혼용하지 않는다.

## F08 장비 관리 1차

관리자 로그인 후 `/admin`의 **장비 관리** 탭 또는 `/admin/equipment`로 진입한다. 장비 검색·분류·운영 상태 필터, 분류 등록, 모델·사양 등록, 개별 장비 등록·수정과 기본 구성품 편집을 제공한다. 신규 장비와 분류는 학생 목록·검색 필터에 반영된다. 기존 모델을 함께 쓰는 장비의 사양은 새 모델을 등록하여 해당 장비에 선택한다.

장비 수정은 현재 버전과 행 잠금을 확인하고, 운영 상태·대여 허용 변경에는 사유와 실제 영향 확인을 요구한다. 등록된 관리번호는 이력 식별자로 유지한다. 진행 중 신청이 있는 장비의 모델·구성품 변경은 관련 신청 처리 완료 후 가능하다. 반납 검수는 저장된 출고 기준을 사용한다.

사용 중지·대여 제한 상태에서는 새 신청·승인·출고를 제한하고 기존 신청과 반납 처리는 유지한다. 사용 중지된 장비의 반납에서 손상·누락을 발견하면 점검 필요 이력을 남기고 중지 상태를 유지한다. 미해결 반납이나 출고와 연결된 미완료 점검이 있으면 정상 복귀를 차단한다. 출고 전 수동 점검은 관리자가 확인하고 정상으로 복귀할 수 있다.

API는 관리자 권한과 CSRF를 적용한 `GET/POST /api/admin/equipment`, `PUT /api/admin/equipment/{id}`, `POST /api/admin/equipment/types`, `POST /api/admin/equipment/models`다. 기존 ERD 테이블·시퀀스를 사용한다.

검증 결과는 다음과 같다.

- 전체 단위 테스트 18개 통과. F08 입력 정책·서비스 회귀 11개와 기존 대여 정책 7개다.
- 실제 Oracle F08 API 11개 검증 통과. 권한·CSRF, 분류·모델·사양·장비 등록, 중복·버전·동시 수정, 중지 후 신규 신청 제한과 기존 이력 보존, 점검 우회 방지·중지 유지, 출고 후 기본 구성품 변경의 스냅샷 독립을 확인했다.
- 실제 Chrome 화면 13개 검증 통과. 관리자 진입, 등록·수정·중지 확인, 정수 입력 검사, 학생 목록·새 분류 필터 반영, 데스크톱·390px 모바일 편집창을 확인했다.
- 기존 추천·가용성 데이터 검사 15개와 JAR 패키징을 통과했다. 이번 합성 검증 계정·장비·분류·모델·신청 등 45행은 고유 식별자로 한정하여 정리했다. 기존 데이터와 초기 자원은 유지한다.

## 신청 상세 보강

학생의 `/records`·`/history`에서 해당 신청 항목의 상세를 열거나 `?item={requestItemId}`로 연결한다. 조회는 기존 `GET /api/requests`의 본인 기록을 사용한다. 진행 단계·상태별 다음 행동, 실제 출고·시설 이용 시각, 출고 구성품과 회차별·누적 반환 및 부족 수량을 표시한다. 예정 시각만으로 처리 완료를 추정하지 않는다. 학생 응답에는 출고·반환 검수의 내부 메모와 관리자 식별정보를 포함하지 않으며 공개 가능한 거절·보류 사유를 구분한다.

## F21 시설 운영 관리

관리자 로그인 후 `/admin/facilities`에서 시설 등록·기본 정보 수정, 요일별 운영 시간·허용 목적, 점검·운영 중지 구간의 추가·수정·삭제를 처리한다. 등록한 시설 관리번호는 변경하지 않는다. 요일은 월요일 1~일요일 7, 시간은 `HH:mm`이며 같은 날 시작보다 늦은 종료 시각을 입력한다. 시간 또는 목적을 비워 두면 이용 가능으로 추정하지 않는다. 비활성 목적의 기존 연결은 보존할 수 있지만 신규 연결은 차단한다.

시설의 `ROW_VERSION`을 시설 정보와 제한 구간 편집이 함께 사용한다. 신청 제출·승인과 동일한 시설 행을 먼저 잠그고 기대 버전과 예약 영향을 확인한 뒤 한 트랜잭션으로 저장한다. 미래의 승인 예약과 종료 처리되지 않은 시설 이용을 보호하며 수용 인원 축소·목적 제거·운영 시간 축소·이용 불허·운영 제한이 충돌하면 `409`를 반환한다. 제한 구간은 시작 포함·종료 제외로 검사한다. 승인 대기는 자원을 확보하지 않으므로 변경 후 승인 시 최신 조건을 다시 검사한다. 기존 신청과 실제 이용 이력은 변경하지 않는다.

| API | 동작 |
| --- | --- |
| `GET /api/admin/facilities` | 시설·목적·요일 시간·기존 제한 구간 조회 |
| `POST /api/admin/facilities` | 시설 등록 |
| `PUT /api/admin/facilities/{id}` | 전체 시설 정보·시간·허용 목적 수정 |
| `POST /api/admin/facilities/{id}/blocks` | 제한 구간 추가 |
| `PUT /api/admin/facilities/{id}/blocks/{blockId}` | 제한 구간 수정 |
| `POST /api/admin/facilities/{id}/blocks/{blockId}/remove` | 제한 구간 삭제 |

변경 요청은 시설의 `expectedVersion`을 보내며 응답의 `facility.version`으로 갱신한다. 운영 상태·이용 허용 변경과 모든 제한 구간 변경에는 사유·실제 확인을 요구한다. 제한 구간의 등록자·최초 등록 시각은 수정 시 보존한다. 구간 등록·수정 사유는 `FACILITY_BLOCK.REASON_TEXT`에 저장한다. 시설 상태 변경·구간 삭제의 별도 감사 이력 저장 기능은 현재 없다.

## F17 대체 장비 관계 관리

관리자 로그인 후 `/admin/alternatives`에서 원래 장비를 선택하고 대체 장비별 지정 사유·주요 차이·활성 여부를 편집한다. 관계는 `A → B` 방향이며 `B → A`를 자동 생성하지 않는다. 자기 자신·중복 대상·존재하지 않는 대상은 거부한다. 사유는 관계마다 필수 500자, 차이는 선택 1000자다. 현재 점검·사용 중지·대여 불허인 장비도 관계는 편집할 수 있으며, 학생의 실제 대체 후보 선택은 별도의 최신 가용성 검사를 따른다.

`GET /api/admin/equipment-alternatives`는 장비와 활성·비활성 관계를 반환한다. `PUT /api/admin/equipment-alternatives/{sourceId}`는 `{expectedVersion, alternatives:[{targetId,reason,difference,enabled}]}` 전체 목록을 받는다. 기존 관계를 빠뜨리면 삭제하지 않고 비활성으로 보존한다. 실제 변경이 있을 때만 원래 장비의 버전을 증가시키고 `CONFIGURED_BY`를 마지막 설정자로 갱신한다. `CREATED_AT`는 최초 등록 시각으로 유지한다. 같은 값으로 저장하면 버전·설정자·시각을 변경하지 않는다.

시설·대체 관계 API에는 기존 관리자 권한·CSRF를 적용한다. 조회는 부모 버전을 자식 데이터보다 먼저 읽어 동시 수정 후 오래된 내용이 최신 버전으로 저장되는 것을 방지한다. 기존 26개 테이블·17개 시퀀스와 이름을 유지했으며 DDL·마이그레이션·초기 데이터 삭제는 수행하지 않았다.

## 개인 홈·모바일 선택 목록

`GET /api/me/summary`는 인증 학생 본인의 항목만 집계한다. `basisDate`·`generatedAt`·`timeZone`과 `counts`의 `pickup`·`returnDue`·`facilityUse`, `todo` 최대 3건을 반환한다. 한국 시각의 하루를 시작 포함·다음 날 시작 제외로 계산하고 승인 대기는 확정 건수에서 제외한다. 할 일은 반납 보류·반납 신청을 먼저 표시하고 이후 현재부터 7일 미만의 예정 행동을 가까운 순으로 채운다. 같은 시각은 항목 ID 순이며 반환 대기 건에 중복 반납을 요구하지 않는다.

홈 카드의 오늘 필터는 해당 본인 신청 목록으로, 할 일은 신청 상세로 연결한다. 모바일은 네이티브 `dialog` 선택 목록에서 조건 편집·제거·신청, 로그인과 최종 확인을 이어간다. 코드와 API 구현을 완료했으나 이번 브라우저 자동화는 `native pipe unavailable (os error 2)`로 연결되지 않았다. 실제 렌더링·실기기·키보드 접근성은 통과한 것으로 보고하지 않는다.

저장소의 순수 회귀 검사는 Node.js로 재실행한다.

```powershell
node tools/check-ui-data.mjs
node tools/check-facility-hours.mjs
node tools/check-personal-home.mjs
```

각각 기존 데이터 15개·시설 시간 8개·개인 홈 10개다. 당일 총 47개는 여기에 `.work/`의 일회성 신청 상세 7개·선택 흐름 7개를 더한 서로 다른 검사 항목 수이며 재실행 횟수의 합이 아니다. 실제 Oracle 신규 합성 시나리오도 `.work/`의 일회성 검증이다. 이 순수 검사들은 실제 DOM·브라우저 검증을 대신하지 않는다.

## 추가 요청: 활동·필요 항목 기반 추천

면접·모의면접 준비·스터디·세미나·행사와 기타 자유 입력을 보강한다. 공간·영상·음성·자료 투사(`space`·`video`·`audio`·`presentation`) 필요를 사용자가 고른다. 활동은 준비 설명이며 시설의 실제 허용 목적이나 승인 권한이 아니다. 기존 일정·수동 인원·허용 목적·선택 목록을 보존하고 시설 신청은 기존 가용성·허용 목적 검사를 따른다. AI 모델 대신 규칙과 사용자 선택을 사용한다.

`GET /api/catalog`는 기존 필드를 유지하고 `purposeRules:[{purposeId,name,keywords:[{keyword,matchMode,effect,priority}],equipment:[{typeName,needLevel,reason}]}]`를 추가한다. 기존 `USE_PURPOSE`·`PURPOSE_KEYWORD`·`PURPOSE_EQUIPMENT_RULE`·`EQUIPMENT_TYPE`에서 활성 목적·키워드·품목만 읽고 개인정보·관리자 식별자는 반환하지 않는다. 서버는 이 DB 규칙을 사용하며 규칙이 비어 있을 때 임의의 DB 정책을 만들지 않는다. 새 DDL·학교 허용 목적·추천 규칙의 임의 등록은 하지 않았다.

이번 추가 개선 후 Java 전체 79개(기존 73개+새 카탈로그 응답 6개), 신규 추천 엔진 순수 검사 16개·UI 대역 검사 14개·실제 Oracle 카탈로그 연계 읽기 6개를 통과했다. 기존 데이터 15개·시설 시간 8개·개인 홈 10개 회귀도 재확인했으며 재실행 횟수를 더해 통과 수를 늘리지 않는다. `node tools/check-purpose-recommendations.mjs`로 신규 엔진 검사를 재실행한다. 이번 추가 검증에서 DB 쓰기·DDL·학교 허용 목적 추가는 하지 않았다.

네이티브 Chrome 앱 제어로 면접 공간 후보·허용 목적 미선택 시 선택 차단, 기타 자유 입력·변경 안내·영상/음성 장비 후보·빈 선택 목록 보존을 데스크톱에서 확인했다. 앞선 네 단계의 브라우저 미검증을 대체하지 않으며 이번 추천 일부 화면만 확인한 결과다. 실제 촬영/녹음·일정 신청 저장은 실행하지 않았고 모바일·전체 키보드 접근성은 미검증이다. 추가 개선의 JAR 패키징·전체 Java 79개와 공개 후보/JAR 비밀값 검사를 통과했다. 앞선 42개·47개 결과와 별도로 기록한다.
