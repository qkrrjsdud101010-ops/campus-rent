# CampusRent 화면 개선 상세 설계

| 항목 | 내용 |
| --- | --- |
| 작성일·버전 | 2026-10-28 · v0.1 |
| 상태 | 사용자 요청으로 채택한 개선의 구현 전 설계안, 팀 검토용 |
| 기준 | [계획서 v0.13](../New-Era_PROJECT.md), [현재 화면](README.md), [Oracle 11g 스키마](../../db/oracle11g/README.md) |
| 화면 검토 | [독립 화면 검토안](campusrent-improvement-wireframes.html)을 브라우저로 열어 구성·클릭 동작 확인 |
| 기술 범위 | HTML·CSS·JavaScript·Thymeleaf, Java·Spring Boot, Oracle 11g |

이 문서의 경로·조회 응답·동작은 후속 구현의 기준이다. 검토안의 수치·일정·이력은 고정된 합성 예시이며 기존 앱의 신청·계정·DB에 연결되지 않는다. 기존 PPT 39장과 Figma는 아직 수정하지 않았다. SQL의 26개 테이블·185개 컬럼을 유지한다.

## 1. 채택 범위와 구현 순서

| ID | 개선 | 관련 기능 | 순서·산출 기준 |
| --- | --- | --- | --- |

29개 기능(필수 24개·선택 5개)의 구분을 유지한다. 위 UX 번호는 추적용이며 기존 Screen ID나 새로운 유스케이스 번호가 아니다. 별도 알림 발송·연체 관리·재신청·반복 예약·사진 업로드 시스템은 이번 범위에 추가하지 않는다. 모바일 보강은 선택 목록과 관련 상세·시간표 이용 흐름에 한정한다.

장비 관리(F08), 대체 장비 관계 편집(F17 관리 부분), 시설 운영 관리(F21)는 기존 필수 개발 범위로 유지한다. 이번 시간표는 운영 정보를 조회하며 운영시간·점검 일정 편집은 F21에서 구현한다.

## 2. 메뉴와 화면 연결

| 기존 경로 | 변경 구성 | 진입·복귀 |
| --- | --- | --- |
| `/` | 로그인 학생에게 오늘 일정 3개 요약·다음 할 일 표시 | 항목 선택 → 해당 신청 상세, 뒤로 → 홈 |
| `/records` | 진행 중 항목의 `신청 상세` 패널 | 홈/목록 → 항목, 닫기 → 원래 목록 위치 |
| `/history` | 종료 항목의 같은 상세 패널, 과거 이력 중심 | 기존 항목 순번과 결과 유지 |
| `/equipment`, `/purpose` | 정보 위계 개선·공통 선택 목록 | 기존 검색·추천 조건 보존 |
| `/facilities` | 자원 카드의 `시간표 보기`, 빈 시간 → 조건 확인 패널 | 일정 확인 후 기존 선택 목록에 반영 |
| `/admin` | 건수 카드 클릭·상태/자원/검색 필터·정렬 | 개별 신청 처리와 기존 검수 패널 유지 |

후속 구현에서는 `/records?item={requestItemId}`, `/history?item={requestItemId}`로 특정 상세를 열 수 있게 한다. 숫자 ID만으로 열람 권한이 생기지 않는다. 로그인 후 현재 상태를 조회해 진행/과거 분류가 바뀌었으면 맞는 목록으로 연결하고, 삭제·권한 오류에는 목록 복귀를 제공한다. 공개 URL에는 신청자 이름·이메일을 넣지 않는다.

## 3. UX01·UX06 — 신청 상세와 상태별 행동

### 3.1 상세 패널 구성

표시 순서:

1. 접수번호·원래 항목 번호·자원 이름·장비/시설 구분·현재 상태.
2. **다음 할 일**: 현재 상태에서 학생이 해야 할 행동 또는 기다리는 처리.
3. **예정 일정**: 장비 수령/반납 예정 또는 시설 이용 예정, 시설 인원·목적.
4. **실제 처리 내역**: 실제 저장된 상태 이력·출고/시설 시작·종료·검수 회차.
5. 장비 출고 기준과 누적 반환·부족 수량, 최근 보류 사유. 상세 회차는 펼쳐 확인.
6. 자원 기본 정보와 허용되는 행동. 자원 기본 상세는 `자원 정보`로 분리해 기존 기능을 보존.

데스크톱 패널은 최대 720px, 모바일은 화면 폭에 맞춰 한 열로 구성한다. 내용은 스크롤할 수 있게 하고 제목·닫기는 항상 접근 가능하게 한다. 닫은 뒤 원래 상세 열기 버튼으로 초점을 돌린다.

진행 단계는 장비 `신청 → 승인 → 출고 → 반환 확인 → 완료`, 시설 `신청 → 승인 → 이용 시작 → 이용 종료`의 안내 구조를 사용한다. 실제 이력은 시간순 목록으로 제공한다. 거절·취소·반납 보류는 분기 상태로 표시하고 진행률 %를 만들지 않는다. 로그가 누락된 과거 기록은 현재 상태와 확인 가능한 이력만 표시하며 중간 단계를 완료했다고 추정하지 않는다. 반납 보류 재확인처럼 같은 상태가 반복된 회차도 생략하지 않는다.

### 3.2 공통 상태·행동 기준

SQL README의 상태 코드는 보완 설계이며 팀 코드 규약 확정 시 함께 맞춘다. 화면 곳곳에서 상태 문자열을 개별 정의하지 않고 자원 종류·역할·상태로 같은 표시 기준을 조회한다. 아래 관리자 행동은 기존 업무 흐름을 설명하며 실제 상태·버전·권한 검사가 성공해야 실행된다.

| 상태 코드 | 학생 표시명 | 다음 할 일·학생 행동 | 관리자 주요 행동 | 표현 |
| --- | --- | --- | --- | --- |
| PENDING | 승인 대기 | 아직 자원 미확보 안내, 본인 항목 취소 가능 | 개별 승인 / 사유 입력 후 거절 | 대기·파랑 |
| APPROVED (장비) | 승인·수령 대기 | 수령 예정 일정 확인, 실제 장소는 관리자 안내 확인 | 출고 검수·출고 기준 보존 | 진행·파랑 |
| CHECKED_OUT | 대여 중 | 반납 예정 일정 확인 / 반납 신청 | 기존 허용 상태의 업무 확인 | 진행·파랑 |
| RETURN_REQUESTED | 반납 신청 | 실제 반환 및 관리자 확인 안내, 중복 반납 신청 없음 | 출고 기준 반환 검수 | 대기·파랑 |
| RETURN_HELD | 반납 보류 | 부족 구성품·수량 확인 후 추가 반환, 새 신청 생성 없음 | 동일 건 추가 반환 재확인 | 주의·주황 |
| RETURNED | 반납 완료 | 결과·실제 검수 내역 조회 | 완료 이력 조회 | 완료·초록 |
| APPROVED (시설) | 예약 승인 | 이용 예정 일정·장소 확인 | 실제 이용 시작 확인 | 진행·파랑 |
| IN_USE | 이용 중 | 시설 이용·종료 안내 확인, 학생 완료 버튼 없음 | 실제 이용 종료 확인 | 진행·파랑 |
| COMPLETED | 이용 완료 | 실제 시작·종료 이력 조회 | 완료 이력 조회 | 완료·초록 |
| REJECTED | 거절 | 거절 사유·처리 시각 확인 | 거절 이력 조회 | 결과·빨강 |
| CANCELLED | 신청 취소 완료 | 취소 결과·시각 조회 | 취소 이력 조회 | 종료·회색 |

상태 태그는 정보이고 행동 버튼과 모양을 구분한다. 색만으로 의미를 전달하지 않으며 상태명과 필요한 설명을 함께 표시한다. 장비의 `점검 중/사용 중지`는 신청 상태와 별도 영역에 표시한다. 예를 들어 `반납 완료`와 `장비 점검 중`이 동시에 존재할 수 있다. 예정 시각 경과·새로고침만으로 상태를 바꾸거나 대기 신청을 확정하지 않는다.

### 3.3 출고·반납 구성품 표시

| 구성품 예시 | 실제 출고 수량 | 누적 반환 수량 | 부족 수량 | 안내 |
| --- | ---: | ---: | ---: | --- |
| 카메라 본체 | 1 | 1 | 0 | 반환 확인 |
| 배터리 | 1 | 0 | 1 | 배터리 1개 추가 반환 필요 |

- 기준은 해당 대여 건의 `CHECKOUT_COMPONENT`다. 현재 기본 구성품을 가져와 과거 기준을 재작성하지 않는다.
- 누적 반환 = 동일 출고·구성품의 회차별 `RETURN_COMPONENT.RETURNED_QTY` 합계. 부족 = 실제 출고 수량 − 누적 반환 수량. 필수 구성품의 부족을 다음 행동에 우선 표시한다.
- 수량을 구성품 단위로 먼저 집계한 뒤 회차·상태 이력과 연결한다. 여러 일대다 테이블을 한 번에 JOIN해 반환량을 중복 합산하지 않는다.
- 최근 검수의 보류 사유·검수 시각을 함께 보여준다. 이전 회차는 별도 펼치기로 확인하고 이번 반환량과 누적 반환량을 구분한다.
- 음수 부족/초과 반환 등 데이터 불일치는 0개로 감추지 않고 `기록 확인 필요`로 표시한다. 쓰기 서비스에서 초과 반환을 차단한다.
- 출고 보존 기준이 없는 과거 건은 `출고 구성품 기록 없음`으로 표시한다. 사후 등록은 `사후 등록`과 등록 시각을 구분하고 실제 출고 시각이 없으면 `기록 없음`으로 둔다.
- 학생에게는 확인된 수량·사유·처리 시각을 보여주고 내부 메모·관리자 계정 식별자는 제공하지 않는다. 보류 해결 후 장비 점검은 기존 관리자 확인 흐름을 거친다.

### 3.4 시각·장소 데이터의 한계

`REQUEST_ITEM.UPDATED_AT`은 최종 수정 시각이며 승인·출고·반납 시각으로 대신 쓰지 않는다. 실제 이벤트는 상태 로그, 출고, 검수, 시설 이용 기록에서 읽는다. 로그에는 기록된 처리 시각, 출고/시설 이용에는 확인된 실제 시각을 구분해 표시한다.

장비 ERD의 `STORAGE_LOCATION`은 **보관 장소**다. 확정 수령·반납 장소나 당시 장소 snapshot이 없으므로 `보관 장소(현재 정보)`로 표시하고 `수령·반환 장소는 관리자 안내를 확인하세요`로 안내한다. 임의의 전화번호·담당자·수령 마감·추가 반환 기한은 만들지 않는다. 시설 위치도 현재 기본 정보라는 점을 유지한다.

## 4. UX02 — 홈의 개인 일정

홈의 기존 목적 입력·직접 검색 진입은 유지한다. 학생 로그인 시 해당 영역 다음, 활동별 소개 앞에 `내 대여·예약` 영역을 추가한다. 비로그인에는 개인 데이터를 요청하지 않고 기존 홈을 제공한다. 관리자에는 학생 요약 대신 기존 관리자 화면 진입을 제공한다.

### 4.1 집계와 표시

기준 시각은 서버의 `Asia/Seoul`이다. 오늘은 `[오늘 00:00, 내일 00:00)`, 내일은 그 다음 하루다. 모든 건수는 신청 묶음이 아닌 **개별 항목 수**다.

| 요약 카드 | 포함 조건 | 누르면 |
| --- | --- | --- |
| 오늘 수령 | 본인 장비·APPROVED·수령 예정 시작이 오늘 | 신청 현황의 해당 항목 목록 |
| 오늘 반납 예정 | 본인 장비·CHECKED_OUT·반납 예정 종료가 오늘 | 신청 현황의 해당 항목 목록 |
| 오늘 시설 이용 | 본인 시설·APPROVED 또는 IN_USE·예정 구간이 오늘과 겹침 | 시설 신청 현황의 해당 항목 목록 |

아래 `다음 할 일`은 최대 3건과 `신청 현황 전체 보기`를 표시한다. 후보는 ① 모든 반납 보류 ② 예정일과 관계없는 모든 반납 신청 ③ 지금부터 7일의 예정 행동이며 이 순서로 채운다. 보류는 최근 검수, 반납 신청은 해당 상태 로그 시각 내림차순으로 정렬한다. 반납 신청 건도 3건 제한에 포함하고 `관리자 반환 확인 대기`로 안내하며 재반납을 요구하지 않는다.

예정 행동은 승인 장비의 수령 시작, 대여 중 장비의 반납 종료, 승인 시설의 이용 시작, 이용 중 시설의 이용 종료 시각을 각각 기준으로 가까운 순으로 표시한다. 같은 시각이면 항목 ID 오름차순으로 정렬하고 같은 항목을 중복 표시하지 않는다. 내일 일정은 `내일 14:00 반납 예정`처럼 날짜를 분명히 쓴다. 3건을 넘는 항목은 전체 보기로 확인하며 요약 카드의 오늘 건수는 이 제한과 관계없이 전체 대상에서 계산한다.

예정 시각이 지났는데 현재 상태가 유지되면 상세에서 `예정 시각 지남 · 현재 처리 상태 확인`을 안내한다. 상태 자동 변경·연체 제재·별도 연체 목록은 추가하지 않는다. 승인 대기는 수령·시설 이용 확정 건수에 포함하지 않는다.

### 4.2 로딩·갱신·접근

- 처음 조회 중에는 `불러오는 중`, 실패하면 `일정을 불러오지 못했습니다`와 재시도. 실패를 0건으로 표시하지 않는다.
- 성공한 0건은 `오늘 예정된 일정이 없습니다`와 기존 장비·시설 탐색 링크를 제공한다.
- 접속·로그인 변경·신청/취소/반납 처리 후·화면 재진입 시 갱신한다. 별도 푸시·메일·실시간 소켓은 요구하지 않는다.
- 서버가 인증된 학생 ID로 집계한다. 다른 사람의 ID를 쿼리로 받아 개인 요약을 반환하지 않는다. 로그아웃 시 이전 요약을 즉시 지운다.

## 5. UX03 — 시설 주간 시간표

### 5.1 화면 구성

시설 카드의 `시간표 보기`로 시설 한 곳을 연다. 상단에 시설명·위치·수용 인원·주간 범위와 이전/다음 주 이동을 제공한다. 주간은 월요일 시작 7일이며 오늘이 속한 주를 기본으로 한다. 인원·목적·이용 길이는 기존 시설 조건을 가져온다.

데스크톱은 월~일 열과 시각 축, 모바일은 날짜 선택과 해당 날짜의 텍스트 시간 목록으로 제공한다. 양쪽은 같은 조회 응답을 사용한다. 시간표 범례는 `빈 시간`, `예약됨`, `운영 제한`, `운영시간 외`, `정보 확인 필요`다. 타인의 이름·학번·이메일·접수번호·이용 목적·활동 내용·관리자 메모는 응답에도 포함하지 않는다.

### 5.2 가용성 규칙

1. 시설의 이용 허용·운영 상태, 요일별 운영 시간, 이용 제한 구간, 확정 예약을 함께 읽는다.
2. 시설 신청 `APPROVED/IN_USE/COMPLETED`는 **원래 예약 구간**을 점유한다. `PENDING/REJECTED/CANCELLED`는 점유하지 않는다. 조기 종료해도 원래 종료까지 유지한다.
3. 구간은 `[시작, 종료)`다. 겹침은 `기존 시작 < 새 종료 AND 기존 종료 > 새 시작`. 14:00 종료 예약과 14:00 시작 후보는 경계만 같으면 충돌하지 않는다.
4. 주간 경계를 넘는 구간은 조회 주간으로 잘라 표시하되 원본 예약 시각은 변경하지 않는다. 겹친 제한·예약은 합쳐 빈 구간을 계산한다.
5. 기본 탐색 단위는 프로젝트 UI 설정값 30분으로 제안한다. 실제 운영 정책 확정 전의 표시 기준이며 점유·제한은 분 단위 원시 구간으로 검사한다. 10:15 시작 제한을 10:30으로 늦춰 빈 시간으로 표시하지 않는다.
6. 운영 시간 행이 없으면 `운영시간 정보 없음`으로 두고 선택하지 못하게 한다. 미설정을 휴무나 종일 이용 가능으로 추정하지 않는다. 당일 종료가 시작보다 이르거나 같은 등 해석 불가 데이터도 확인 필요로 처리한다.
7. 실제 휴일·익일 운영·준비/정리 시간 규칙은 확정 전이다. 현 ERD에 별도 휴일 달력이 없으며 등록된 이용 제한으로만 표시한다.
8. 시간표가 비어 보여도 인원·목적·길이가 미입력되면 `시간 여유 있음 · 조건 입력 후 확인`으로 표시한다. 조건 불충족·과거 시각·시설 제한 상태·조회 실패는 선택 가능으로 표시하지 않는다.

`조회 시점 가능`은 확보 보장이 아니다. 조회 시각과 재조회 버튼을 제공하고 제출·승인 시 다시 검사한다. 별도 실시간 갱신을 가정하지 않는다.

### 5.3 빈 시간 선택

- 시작 후보를 누르면 기존 이용 길이에 따른 종료 시각·인원·목적을 조건 확인 패널에 표시한다. 연속 구간 전체가 가능해야 한다.
- 직접 탐색 중 길이가 없으면 시작·종료를 먼저 입력받는다. 인원·목적도 완료한 뒤 선택 목록에 담을 수 있다.
- F25의 `다른 이용 시간대`에서 진입했다면 같은 시설·기존 길이·인원·목적을 유지한다. 유지 조건을 바꾸려면 원래 조건 편집 흐름으로 돌아간다.
- 확인 후 해당 항목의 초안만 변경한다. 같은 자원이 이미 담겼으면 기존 조건과 바뀔 조건을 보여주고 명시적으로 적용하며 다른 항목은 유지한다.
- 신청·로그인은 기존 별도 단계다. 서버에서 새 충돌을 발견하면 기존 선택·입력을 보존하고 충돌 사유와 재조회 경로를 표시한다.

## 6. UX04 — 관리자 업무 필터와 정렬

기존 `/admin`의 2개 카드를 키보드로 누를 수 있는 버튼으로 변경한다. 접근 가능한 이름은 `승인 대기 N건 보기`, `장비 반납 신청 N건 보기`다. 카드는 화면의 전체 조회 권한 범위에서 집계한 개별 항목 수다.

| 카드 | 클릭 후 필터 | 기본 정렬 |
| --- | --- | --- |
| 처리할 승인 대기 | 종류 전체·상태 PENDING·검색어 비움 | 오래된 신청순 |
| 장비 반납 신청 | 종류 장비·상태 RETURN_REQUESTED·검색어 비움 | 오래된 신청순 |

카드 클릭 시 기존 검색·종류 필터를 초기화해 카드 수와 결과 수를 맞추며 변경된 필터를 화면에 명확히 보여준다. 이후 검색·종류·상태를 바꾸면 `전체 승인 대기 N건 / 현재 조건 M건`처럼 전체 카드와 필터 결과를 구분한다. 필터 초기화 버튼을 제공한다. 카드의 0건도 누를 수 있고 해당 상태의 빈 결과를 안내한다.

정렬 선택은 `오래된 신청순`, `최신 신청순` 두 가지다. 기준은 `RENT_REQUEST.REQUESTED_AT`이며 같은 시각에는 `REQUEST_ID`, `REQUEST_ITEM.ITEM_NO`로 순서를 고정한다. 상태 변경 시각·반납 신청 시각 순이라고 표시하지 않는다. 초기 진입은 오래된 신청순으로 하고 사용자 선택은 해당 화면 이용 중 유지한다.

새로고침·개별 처리 후에는 최신 집계와 목록을 함께 갱신한다. 분리 조회 시 동일 읽기 기준으로 묶거나 한 응답으로 반환해 숫자의 시점을 맞춘다. 성공한 처리 항목이 현재 필터에서 사라지면 처리 결과를 알리고 목록 제목으로 초점을 이동한다. 정렬·필터는 조회만 바꾸며 승인이나 일괄 처리를 실행하지 않는다.

## 7. UX05 — 모바일 선택 목록

### 7.1 화면과 상호작용

기존 CSS 기준 768px 미만에서 하단에 `선택한 자원 N개 · 목록 보기` 버튼을 표시한다. N은 장비와 시설을 합한 선택 항목 수이며 중복 DOM을 위한 별도 선택 데이터를 만들지 않는다. 데스크톱에서는 기존 우측 패널을 사용한다.

1. 목록 열기 → 제목·닫기·항목별 자원명·종류별 일정·시설 인원/목적·조건 상태를 표시.
2. 항목의 조건 수정·제거 → 같은 선택 상태에 반영, 수량과 목록 즉시 갱신.
3. `신청 내용 확인` → 필요한 인증 → 최종 확인 → 별도 최종 제출의 기존 흐름 유지.
4. 목록 닫기/뒤로 → 입력·선택·원래 탐색 위치 유지, 열기 버튼으로 초점 복귀.

0개일 때도 `선택한 자원 0개 · 목록 보기`로 빈 목록을 열 수 있지만 신청 진입 버튼은 제공하지 않는다. 빈 상태에서 기존 장비·시설 목록으로 돌아갈 수 있다. 입력 미완료 항목은 `조건 입력 필요`와 수정 경로를 표시하며 목록 수에 포함한다.

### 7.2 가림·초점·오류

- 본문 끝에 하단 버튼 높이와 안전 영역만큼 여백을 둔다. 토스트·오류·목록의 최종 버튼이 겹치지 않도록 배치한다.
- 패널이 열리면 하단 열기 버튼은 숨기고 패널 내부 버튼을 사용한다. 네이티브 dialog 등으로 배경 조작을 제한하고 Escape/닫기를 지원한다.
- 모바일 키보드가 열리면 편집 중인 입력과 확인 버튼이 보이게 하고 필요하면 하단 열기 버튼을 일시 숨긴다.
- 닫기·창 크기 변경·다른 상세 진입을 포함해 같은 데이터로 복원한다. 최종 제출 중 중복 클릭을 차단하고 실패 시 기존 선택을 유지한다.
- 조작 영역은 약 44px 이상, 레이블은 화면에 보이게 한다. 입력 오류는 해당 항목 가까이 표시하고 첫 오류로 초점을 이동한다.

## 8. UX07 — 자원 카드와 공통 시각 기준

### 8.1 카드 정보 순서

| 순서 | 장비 | 시설 |
| --- | --- | --- |
| 1 | 확인된 사진 또는 기존 아이콘, 이름·관리번호 | 확인된 사진 또는 기존 아이콘, 이름·시설 코드 |
| 2 | 현재 적용 조건의 이용 가능 여부·불가 이유 | 현재 적용 조건의 가능 여부·불가 이유 |
| 3 | 모델·핵심 사양 최대 2개 | 수용 인원·위치·대표 비치 설비 |
| 4 | 보관 장소(현재 정보) | 운영 시간 요약 |
| 5 | 선택, 상세, 불가 시 다른 기간·대체 장비 | 선택, 상세·시간표, 불가 시 다른 시간·시설 |

모델별 사양은 기존 표시 순서를 사용한다. 긴 사양·전체 구성품·모든 설비는 상세에서 확인한다. 추천 카드에는 추천 이유를 유지하며 핵심 이유가 잘리지 않게 한다. 불가 카드는 회색 처리만 하지 말고 원인과 대안 버튼을 보여준다.

일정 미입력 시 `일정 선택 후 확인`, 조건 변경 미적용이면 `변경한 조건을 적용하세요`, 실패 시 `확인하지 못함`을 표시한다. 불완전한 조회를 `이용 가능`으로 표현하지 않는다. 사진 경로가 없는 현재 ERD를 유지하며, 검토 가능한 실제 사진을 확보하기 전에는 기존 아이콘을 사용한다. 사진 저장·업로드·관리자 편집은 후속 설계 대상이다.

### 8.2 공통 표현

- 기존 파랑 계열 브랜드·폰트·둥근 패널을 유지한다. 상태 의미에만 파랑/주황/초록/빨강/회색을 일관되게 사용하고 장식용 상태색을 늘리지 않는다.
- 한 영역의 주요 행동을 하나로 강조하고 취소·닫기·상세는 보조 버튼으로 구분한다. 위험한 작업은 구체적인 동사와 결과 확인을 제공한다.
- 날짜는 상대 표현과 절대 날짜를 함께 확인할 수 있게 한다. 예정 일정과 실제 처리 내역의 제목을 분리한다.
- 일반 본문은 14px 이상, 상태·필수 안내도 읽을 수 있는 크기로 유지한다. 키보드 초점을 명확히 표시하고 이름 없는 아이콘 버튼을 만들지 않는다.
- 상태 태그는 클릭 기능을 기대하게 만들지 않는다. [GOV.UK 태그 지침](https://design-system.service.gov.uk/components/tag/)과 [W3C 입력 알림 지침](https://www.w3.org/WAI/tutorials/forms/notifications/)을 참고한다. 이 설계만으로 접근성 적합성 검증을 마쳤다고 주장하지 않는다.

## 9. 기존 ERD 연결과 조회 응답

### 9.1 데이터 매핑

| 표시/연산 | 테이블·컬럼 | 주의 |
| --- | --- | --- |
| 본인 소유·접수·원래 항목 번호 | RENT_REQUEST.APPLICANT_ID / REQUEST_NO / REQUESTED_AT, REQUEST_ITEM.REQUEST_ITEM_ID / ITEM_NO | 서버 인증 사용자로 소유권 제한, 항목 기준 집계 |
| 상태·예정 일정·시설 조건 | REQUEST_ITEM.STATUS_CODE / USE_START_AT / USE_END_AT / PEOPLE_COUNT / PURPOSE_ID | UPDATED_AT을 이벤트 발생 시각으로 쓰지 않음 |
| 처리 이력·거절 사유 | REQUEST_STATUS_LOG.FROM_STATUS / TO_STATUS / CHANGED_AT / REASON_TEXT | CHANGED_AT, STATUS_LOG_ID 순; 학생 응답은 허용 필드만 |
| 실제 출고·이름 보존 | EQUIPMENT_CHECKOUT.CHECKOUT_ID / ACTUAL_CHECKOUT_AT / REGISTERED_AT / SOURCE_CODE / ASSET_CODE_SNAPSHOT / EQUIPMENT_NAME_SNAPSHOT | 실제 시각 NULL과 사후 등록을 구분 |
| 출고·반환 수량 | CHECKOUT_COMPONENT.DELIVERED_QTY / REQUIRED_YN, RETURN_COMPONENT.RETURNED_QTY | CHECKOUT_ID + COMPONENT_SEQ 단위 선집계 |
| 보류 사유·회차 시각 | RETURN_INSPECTION.INSPECTION_ROUND / INSPECTED_AT / HOLD_REASON / OUTCOME_CODE | 최신 회차가 우선, 내부 NOTE_TEXT 기본 미노출 |
| 시설 실제 이용 | FACILITY_USAGE.STARTED_AT / ENDED_AT | 미기록 종료를 예정 종료로 대체하지 않음 |
| 자원 현재 위치·사양 | EQUIPMENT.STORAGE_LOCATION, EQUIPMENT_MODEL, MODEL_SPEC, SPEC_ITEM; FACILITY.LOCATION_TEXT / CAPACITY / FIXED_EQUIPMENT_INFO | 장비 보관 장소와 수령/반납 장소 구분 |
| 시설 가능 구간 | FACILITY.USE_ALLOWED_YN / OPERATING_STATUS, FACILITY_HOURS, FACILITY_BLOCK, 시설 REQUEST_ITEM | 확정 상태의 원래 일정 사용, 타인 신청 정보 미투영 |
| 선택 초안 | 현재 sessionStorage 선택 모델, 선택적 서버 연동 시 SELECTION_ITEM | 비로그인 임시 저장과 서버 소유권 구분 |

새 상태·사진·요약 건수·부족 수량 컬럼은 만들지 않는다. 표시명·다음 행동·요약·빈 시간은 서버 조회 및 화면 상태에서 파생한다. DB의 TIMESTAMP에는 시간대가 없으므로 애플리케이션과 DB 연결의 시각 해석을 Asia/Seoul로 일치시킨다. 연산 중 UTC와 현지 시각을 섞지 않는다.

### 9.2 후속 서버 읽기 계약 초안

아래 API는 **설계용 이름**이며 현재 구현·배포된 경로가 아니다. 기존 서비스 연결 방식이 확정되면 Thymeleaf 모델/JSON 중 맞는 형태로 적용한다.

| 읽기 계약 | 응답에 필요한 정보 | 접근·오류 |
| --- | --- | --- |
| `GET /api/me/summary` | 기준일·조회 시각·오늘 카드별 항목 수·다음 할 일·항목 연결 | 학생 세션만, userId 파라미터 없음 |
| `GET /api/me/request-items/{id}` | 현재 상태/버전·예정 조건·허용 행동·실제 이력·출고 기준·회차별/누적 반환·보류/거절 사유 | 본인 소유 확인, 다른 사용자 정보 미반환 |
| `GET /api/facilities/{id}/availability` | 주간 시작·조회 시각·운영/점유/제한/빈 구간·조건 충족 여부·미설정 이유 | 비로그인 가능, 공용 정보만 반환 |
| `GET /api/admin/request-items` | 권한 범위 전체 카드 수·필터 결과 수·항목 목록·현재 정렬·페이지 | 관리자 세션만, 카드/목록 읽기 기준 일치 |

시설·월요일 날짜만으로 공용 운영/점유 시간표를 조회할 수 있다. 이용 길이·인원·목적은 선택 입력이며 제공된 값의 형식·범위를 검증한다. 이 조건이 모두 입력되고 시설 운영 조건도 충족해야 선택 가능한 후보를 반환한다. 미입력은 조회 오류 대신 `조건 입력 필요`, 수용 인원·허용 목적 불충족은 `조건 불충족`으로 구분한다. 관리자 조회는 종류·허용 상태·정렬·페이지를 검증하고 검색·정렬 값을 SQL 문자열에 그대로 이어 붙이지 않는다. 11g 페이지 조회는 해당 버전의 ROWNUM 또는 ROW_NUMBER 방식을 사용한다. 실제 예약 중복 방지는 조회 응답이나 UI 제어에 맡기지 않고 기존 승인 트랜잭션에서 수행한다.

읽기 실패는 `로딩/빈 결과/접근 불가/오류`로 구분한다. 개인·관리자 응답은 권한별 필드 목록으로 직렬화하고 브라우저 영구 캐시에 저장하지 않는다. 타인의 데이터는 내려받은 뒤 숨기는 방식으로 처리하지 않는다. 변경 작업은 기존 인증·소유권·상태·버전·트랜잭션 기준을 그대로 유지한다.

| A12 | 360/390/768/1440px·가상 키보드·320px/확대 재배치 | 가로 넘침·본문/오류/최종 버튼 가림 없음, 같은 선택 상태 유지 |

1차에서는 UX06 공통 표시 → UX01 상세 → UX05 모바일을 구현하고 A01~A04·A05의 개인 상세 접근·A12~A13의 상세/선택 목록 사례를 확인한다. 2차는 UX02·UX04·UX07과 A05~A07의 홈 사례·A11·A14를 검증한다. 3차는 UX03과 A07~A10의 시간표 사례·A12~A13의 시간표 사례를 검증한다. A15의 관련 회귀 사례는 각 단계에 적용한다. 기존 F08·F17·F21과 서버/DB 필수 구현 일정은 별도로 유지한다. 새 구현이 생기면 관련 검증만 추가하고 현재 통과한 시연 검사를 반복해서 완료로 보고하지 않는다.

## 12. 이번 작성·검토 기록

- 계획서 v0.13에 7개 개선과 기존 Fxx 대응·개발 범위·수용 기준을 반영했다.
- 테이블·컬럼 매핑과 상태·가용성·출고/반납 집계 규칙을 SQL 및 현재 소스와 대조했다.
- 독립 화면 검토안은 구성·클릭 동작 확인용이다. 실제 앱 구현/서버 인증/Oracle 실행 검증은 후속 작업이다.
- 독립 검토안의 5개 화면을 360·390·768·1440px에서 열어 가로 넘침을 검사했다. 예시 장비 상태 8종, 선택 제거·잘못된 일정 차단, 빈 시간 조건 확인·구간 밖 입력 차단, 관리자 필터·정렬을 Chrome에서 확인했다. 데스크톱 신청 상세/시간표와 모바일 선택 화면의 캡처를 시각 검토했다. 이 결과는 위 A01~A15의 실제 앱·서버 시험을 대신하지 않는다.
- 기존 PPT·Figma·ERD PDF·DDL·앱 소스는 이번 설계 작업에서 수정하지 않는다.
